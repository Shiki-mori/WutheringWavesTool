# 设计阶段

随着需求变更，本项目需要重构数据库。

## 原始数据表

| Field        | Type        | Null | Key | Default            | Extra         |
|--------------|-------------|------|-----|--------------------|---------------|
| id           | bigint(20)  | NO   | PRI |                    | auto_increment|
| uid          | varchar(50) | YES  | MUL |                    |               |
| resource_id  | varchar(30) | YES  |     |                    |               |
| resource_name| varchar(100)| YES  |     |                    |               |
| is_up        | tinyint(1)  | YES  |     |                    |               |
| quality_level| int(11)     | YES  |     |                    |               |
| pool_type    | int(11)     | YES  |     |                    |               |
| time         | datetime    | YES  |     |                    |               |
| in_second_seq| int(11)     | YES  |     |                    |               |
| created_at   | datetime    | YES  |     | current_timestamp()|               |
| draw_order   | bigint(20)  | YES  |     |                    |               |

原数据表没有经历过设计阶段。

id是记录编号；  
uid是用户的游戏账号id；  
resource_id是记录的id，由链接返回，相同的抽卡元素有相同的id；  
resource_name是记录的名称；  
is_up判断记录是否为up，仅当quality_level为5时存在该判定。不是原始属性，而是后期计算得出；  
quality_level标识记录的品质等级；  
pool_type标识记录的卡池类型；  
time标识抽卡时间；  
in_second_seq标识“在一次十连（或多连等同一time抽取的记录）中的顺序”；  
created_at标识记录的导入数据库时间；  
draw_order记录记录的抽取顺序。抽取顺序不是原始属性，由time以及in_second_seq共同计算得出。

后续可能创建用户登录系统，一个用户可能拥有多个uid游戏账号。

后续将添加手动导入功能，允许用户手动添加抽卡记录，需要与从链接进行的导入进行区分与去重。

以下字段由转发请求返回：

cardPoolType  
count(所有记录固定为1)  
name  
qualityLevel  
resourceId  
resourceType  
time

请求载荷示例：

cardPoolId: "2e23eba1044f1f740cddb72f3b982768"  
cardPoolType: 1  
languageCode: "zh-Hans"  
playerId: "123313309"  
recordId: "90caafa4e6d51a2089b4e835b03ce024"  
serverId: "76402e5b20be2c39f095a152090afddc"  

is_up,draw_order后期计算得出。  
is_up通过简单匹配得出，draw_order通过顺序计算。

增加手动导入功能之后，必须将两种方式区分开。需要为api导入的顺序和手动导入的顺序分别设置字段。
